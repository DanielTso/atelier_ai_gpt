### Model Registry & Cost Visibility

Spec: `docs/specs/2026-07-21-dynamic-model-registry-design.md`. Replaces what used to be a hardcoded Claude model list duplicated across the models route, request validation, 14 personas, and the effort pill — every new Anthropic release meant editing ~6 files by hand. Verified live against the real Anthropic API: Opus 5 appeared in the picker with **zero code change**.

- **Registry** (`src/lib/models/`): `registry.ts`'s `getModelRegistry()` fetches the live catalog (`fetch.ts` → `GET https://api.anthropic.com/v1/models`, paginated via `after_id`/`has_more`, 5s timeout) under the configured Anthropic key, normalizes + prices every model (`normalizeAnthropicModel`), and degrades to a hand-authored `STATIC_SEED` (`seed.ts` — Opus 4.8/Fable 5/Sonnet 5/Haiku 4.5) on any fetch failure so the picker is never empty. In-process cache, TTL 5 min for a confirmed live catalog / 60s for a degraded one (a transient outage self-heals fast rather than sticking for the full 5 min); `clearModelRegistryCache()` invalidates it after an API-key or pricing-override edit. `curateCatalog()` (`curate.ts`) reduces the full catalog to the single newest entry per family (preferring a non-dated-snapshot id, falling back to a dated one only if a family has no undated entry at all), ordered `opus`/`fable`/`sonnet`/`haiku` then newest-first for any unrecognized family — that curated list is what `GET /api/models` serves and what `resolveTier()` searches against.
- **Alias-vs-dated landmine**: the live catalog frequently ships a family with **only a dated snapshot id** and no bare alias (e.g. `claude-haiku-4-5-20251001`, no `claude-haiku-4-5`), while personas/seed/`projects.default_model`/settings all reference the bare alias. `registerDatedAliases()` indexes the derived bare-alias form into `byId` pointing at the same `CatalogModel` (never overwriting a real bare entry, never added to the curated picker list). **Any model lookup by id must go through `registry.byId` / `resolveRequestedModel()`** — a lookup that assumes a bare alias previously made every Haiku request silently resolve to Opus (5× cost) with only a console warning.
- **Never-throw resolvers**: `resolveRequestedModel(requested?)` and `getModelCapabilities(modelId)` never throw. An empty/no request returns the current default; a known id (curated, full raw catalog, `LEGACY_PINS`, or Gemini) passes through; an unknown/retired/tampered id falls back to the default (`console.warn`, `usedFallback: true`) instead of 400ing the request — this is the fix for a real bug where a stale `projects.default_model` dead-ended the chat. The default is the first **Anthropic** entry in `curated`, never `curated[0]` literally (with a Gemini-only key, `curated[0]` could be the image model).
- **Pricing** (`pricing.ts`) resolves in order: a DB override (`settings` key `model-pricing-overrides`, JSON, **validated per-entry** — non-finite/malformed rates are dropped with a warn rather than freezing `NaN` into cost rows) → `EXACT_PRICING` (hand-maintained, current ids only — e.g. Sonnet 5 at the $3/$15 standing rate; the table has no date logic, so an expiring rate must be hand-edited on the day, or corrected without a deploy via the override row) → `FAMILY_TIER_PRICING` (`estimated: true`) → a conservative Opus-tier default with a warn for a totally unrecognized family. Non-Anthropic models (Nano Banana 2) skip this chain entirely and keep a `{0, 0, estimated: true}` "not token-priced" sentinel (it's priced per-image) — `repriceModel()`'s provider guard prevents Gemini from being run through the Anthropic pricing chain and fabricating a false estimate. The picker (`ModelSelect.tsx`) renders each model's rate (`~$X / $Y` + an "est." chip when inferred, or "per image" for the sentinel — never `$0.00`, which would read as free).
- **Capability-driven effort**: `Effort` is one shared union (`src/types.ts`): `'low' | 'medium' | 'high' | 'xhigh' | 'max'` (`providers.ts` and `usePersonas.ts` both re-export it rather than each declaring their own copy, as before this feature). `xhigh` sits between `high` and `max` and is Anthropic's recommended default for coding/agentic work on Opus 5/Sonnet 5/Fable 5. Which levels a given model actually accepts is derived from the live `capabilities.effort.<level>.supported` tree (`mapCapabilities()` in `registry.ts`) into `ModelCapabilities.effortLevels` — never a name-prefix guess. `EffortPill` only offers the levels the *currently selected model* supports (its `levels` prop), and `selectedEffort` is clamped on model switch since it's otherwise model-independent React state that could carry `xhigh` onto a model that 400s on it.
- **Persona tiers** (`src/hooks/usePersonas.ts`) — see `docs/PERSONAS.md` for the user-facing roster. 13 of the 14 built-in personas set `model` to a `ModelTier` (`'flagship' | 'opus' | 'sonnet' | 'haiku'`, `src/lib/models/types.ts`) instead of an exact id, so they auto-adopt Anthropic's newest release in that family. `tierFamily(tier)` maps `'flagship'` → the `fable` family (the one irregular mapping) and every other tier to its same-named family — a single pure helper shared by the server-only `resolveTier()` (`registry.ts`) and the client `resolvePersonaModel()`/`resolvePersonaModelLabel()` so the semantics can't drift between the two copies. **Resolution is client-side**, against the `models` list `page.tsx` already fetches from `GET /api/models` — `resolveTier()` reads API keys via `@/lib/settings` and is server-only, never imported into the `'use client'` hook. `resolvePersonaModelLabel()` prefers the matched row's real `name` over a static id→label map, so a dated-only id still renders a clean display name ("Claude Haiku 4.5"), never the raw "haiku-4-5-20251001". **Contract Abstract stays pinned to the exact `claude-fable-5`** — its locked 22-field extraction schema must not shift under a silent tier-following model swap.
- **Cost capture** (spec §C6) — `src/lib/usage.ts`'s `recordUsage()` writes one best-effort `usage_events` row (see Database section for the column shape; migration `0018`, **applied to Supabase 2026-09-11**) per LLM generation, called from **six capture sites**: `POST /api/chat` (`purpose: 'chat'`, `totalUsage` summed across the whole tool-call loop), `POST /api/artifacts/[id]/regenerate` (`'artifact-regenerate'` — real Claude spend, not free housekeeping), plus the four Gemini Flash housekeeping routes (`summarize`, `generate-title`, `classify`, `memory-suggest`). Every call site is `void recordUsage({...}).catch(() => {})` — a usage-write failure never fails the request that generated the tokens. In `/api/chat` the write goes through `after()` from `next/server` (fire-and-forget fallback outside a request scope), `streamText` gets `abortSignal: req.signal` + an `onAbort` that records the completed steps via `sumUsage()`, and `result.consumeStream()` drains the stream server-side — so a Stop, tab close, or mid-stream provider error still yields exactly one usage row and cancels the upstream generation. A per-request first-wins guard keeps it to exactly one row even though the SDK fires both `onAbort` and `onFinish` on a mid-tool-loop abort, and no row is written when tokens are unknown (abort before any step completed).
- ⚠️ **Cache-token accounting** — settled by reading the *installed* `@ai-sdk/anthropic@3.0.98` source (`dist/index.mjs`), not public docs, which mix SDK versions: `usage.inputTokens` is the SDK's **inclusive** sum of fresh + cache-read + cache-write input, even though Anthropic's own API reports the three as mutually exclusive. A naive `inputTokens × rate + cacheRead × 0.1 × rate + cacheWrite × 1.25 × rate` formula **double-counts every cached token**, worst on exactly the long-context project chats this app targets. `usageTokens()` (`usage.ts`) derives the fresh count from `usage.inputTokenDetails.noCacheTokens` directly (falling back to `inputTokens - cacheRead - cacheWrite` only if that field is absent — `usage.inputTokens` is never used raw); `usage.cachedInputTokens` is deprecated in this SDK version and never read. `estimateCost()` applies the documented cache multipliers (read ×0.1, write ×1.25 of the input rate) to the correctly-split counts.
- **Settings → Usage tab** (`UsageSettingsTab.tsx`, in `SettingsDialog.tsx`) shows monthly spend by model for the trailing 3 months (`getMonthlyUsageByModel()` in `actions.ts`, bucketed `AT TIME ZONE 'UTC'` before `to_char` so the grouping is independent of the Postgres session's timezone) — a per-model thin bar list per month, reusing the `ProjectDefaultsDialog` bar idiom but with a trailing dollar figure instead of a percentage. An always-unpriced row (the `gemini-3.5-flash` housekeeping sentinel: `cost_usd=0, cost_estimated=true`) renders as **"unpriced,"** never "$0.00" (`isUnpricedUsage()` in `utils.ts`) — that tuple is otherwise indistinguishable from a genuine free Claude generation and would misleadingly read as "free." `formatUsd()` (`utils.ts`) shows up to 8 decimals for sub-cent costs (matching `cost_usd`'s own `numeric(12,8)` scale) so a real $0.00003 charge is never rounded away to the same "$0.00" a `toFixed(2)` would give it. Per-chat spend surfaces in `ChatContextMenu` ("Cost: $X.XX", lazily fetched via `getChatCost(chatId)` only when the menu opens — not on every sidebar render) — `getChatCost` sums every `usage_events` row tied to the chat (all purposes, not just chat turns) and excludes `cost_usd=0` rows from its `estimated` flag so a chat that only ever triggered free housekeeping (nearly every chat, via `generate-title`) doesn't misreport "(est.)" on a genuine $0 figure. `ChatContextMenu`'s `@/app/actions` import is **dynamic**, not static — a static import pulls `@/db` into jsdom test renders that don't mock it and throws on a missing `DATABASE_URL`; `UsageSettingsTab.tsx` has the identical hazard via a static import and is only latent because no test currently renders `SettingsDialog` (a shared `@/db` test mock is a queued follow-up, not built here).
