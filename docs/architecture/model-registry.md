### Model Registry & Cost Visibility

Spec: `docs/specs/2026-07-21-dynamic-model-registry-design.md`. Replaces what used to be a hardcoded Claude model list duplicated across the models route, request validation, 14 personas, and the effort pill — every new Anthropic release meant editing each of those by hand. Verified live against the real Anthropic API: Opus 5 appeared in the picker with **zero code change**.

- **Registry** (`src/lib/models/`): `registry.ts`'s `getModelRegistry()` fetches the live catalog (`fetch.ts` → `GET https://api.anthropic.com/v1/models`, paginated via `after_id`/`has_more`, 5s timeout) under the configured Anthropic key and normalizes + prices every model (`normalizeAnthropicModel`). `registry.source` says where the Claude half came from:
  - `'live'` — this build's own fetch.
  - `'stale'` — the fetch failed, so the **last successful live catalog in this process** is served again, re-priced with the current overrides (audit B12: one failed refresh used to swap the live catalog for the seed, silently re-routing a live-only id such as `claude-opus-5` to the seed default and nulling project defaults).
  - `'seed'` — the fetch failed and there has never been a live build in this process: the hand-authored `STATIC_SEED` (`seed.ts` — the current newest model per family, Opus 5.5 / Fable 5.2 / Sonnet 5.5 / Haiku 5.5, from the `claude-api` skill), so the picker is never empty. The previous seed generation (`SEED_ROUTABLE`: Opus 4.8, Fable 5, Sonnet 5, Haiku 4.5) stays routable in `byId` on this path only, never in the picker, so an id a chat, persona or project default already holds keeps its model — Contract Abstract's `claude-fable-5` included.

  Only `'live'` proves an id is absent from Anthropic's catalog. In-process cache, TTL 5 min for `'live'` / 60s for `'stale'` or `'seed'` (a transient outage self-heals fast rather than sticking for the full 5 min). Callers that miss the cache at the same time **share one in-flight build** (one `/v1/models` round-trip on a cold start under load). `clearModelRegistryCache()` invalidates the cache after an API-key or pricing-override edit (every `setSetting`/`setSettings`); a build already in flight when it is called still answers its waiting callers but is never cached. A plain clear keeps the last good live catalog as the fallback for the rebuild; `clearModelRegistryCache({ includeLastGood: true })` drops it too (tests). `curateCatalog()` (`curate.ts`) reduces the full catalog to the single newest entry per family (preferring a non-dated-snapshot id, falling back to a dated one only if a family has no undated entry at all), ordered `opus`/`fable`/`sonnet`/`haiku` then newest-first for any other family — that curated list is what `GET /api/models` serves and what `resolveTier()` searches against. `parseFamily()` reads both `claude-<family>-…` and the legacy version-first `claude-3-7-sonnet-…` form; an id it cannot parse becomes family `'other'`, which is curated as one extra row of its own (newest `'other'` id) and priced at the conservative Opus tier.
- **Alias-vs-dated landmine**: the live catalog frequently ships a family with **only a dated snapshot id** and no bare alias (e.g. `claude-haiku-4-5-20251001`, no `claude-haiku-4-5`), while personas/seed/`projects.default_model`/settings all reference the bare alias. `registerDatedAliases()` indexes the derived bare-alias form into `byId` pointing at the same `CatalogModel` (never overwriting a real bare entry, never added to the curated picker list). **Any model lookup by id must go through `registry.byId` / `resolveRequestedModel()`** — a lookup that assumes a bare alias previously made every Haiku request silently resolve to Opus (5× cost) with only a console warning. `resolveRequestedModel()` returns the id of the catalog entry it matched (prior audit C3), so a bare alias of a dated-only model reaches the provider as the dated id Anthropic actually serves, and the usage row records that id.
- **Never-throw resolvers**: `resolveRequestedModel(requested?)` and `getModelCapabilities(modelId)` never throw. An empty/no request returns the current default; a known id (curated, full raw catalog, `LEGACY_PINS`, `SEED_ROUTABLE` on the seed path, or Gemini) resolves to its catalog entry's id; an unknown/retired/tampered id falls back to the default (`console.warn`, `usedFallback: true`) instead of 400ing the request — this is the fix for a real bug where a stale `projects.default_model` dead-ended the chat. The default is the first **Anthropic** entry in `curated`, never `curated[0]` literally (with a Gemini-only key, `curated[0]` could be the image model); with no Anthropic entry at all it is the seed's first id (`claude-opus-5-5`). `updateProjectDefaults` nulls an unrecognized `defaultModel` only while `registry.source === 'live'`; under a stale or seed registry it keeps the id as given.
- **Pricing** (`pricing.ts`) resolves in order: a DB override (`settings` key `model-pricing-overrides`, JSON, **validated per-entry** — non-finite/malformed rates are dropped with a warn rather than freezing `NaN` into cost rows; an optional finite `cacheReadPerMTok` is kept) → `EXACT_PRICING` (hand-maintained from the `claude-api` skill and Anthropic's pricing page, still-served ids only: Opus 5.5 $4/$20, Opus 5 and 4.8 $5/$25, Fable 5.2 $8/$40, Fable 5.1 and 5 $10/$50, Sonnet 5.5 and 5 $2/$10 — the scheduled Sonnet 5 increase to $3/$15 was cancelled — Haiku 5.5 $0.10/$0.50, Haiku 4.5 $1/$5; the table has no date logic, so a price change must be hand-edited on the day, or corrected without a deploy via the override row) → `FAMILY_TIER_PRICING` (`estimated: true`) → a conservative Opus-tier default with a warn for a totally unrecognized family. The override and exact lookups try the id itself, then its **bare alias** (audit B19), so a dated-only catalog id such as `claude-haiku-4-5-20251001` prices from the `claude-haiku-4-5` row with `estimated: false` and an alias-keyed override applies to it; an entry for the exact dated id still wins. `ModelPricing.cacheReadPerMTok` is set only where the cache-hit rate is not the standard 0.1× of input (Opus 5.5 and Sonnet 5.5 are 0.05×, Fable 5.1/5.2 0.025×); cache writes are 1.25× input everywhere. Haiku 5.5's over-100K-token rate ($0.50/$2.50) is not modelled: a row is priced from step-summed usage, which cannot tell a long request apart, so such requests are under-costed. Non-Anthropic models (Nano Banana 2) skip this chain entirely and keep a `{0, 0, estimated: true}` "not token-priced" sentinel (it's priced per-image) — `repriceModel()`'s provider guard prevents Gemini from being run through the Anthropic pricing chain and fabricating a false estimate. The picker (`ModelSelect.tsx`) renders each model's rate (`~$X / $Y` + an "est." chip when inferred, or "per image" for the sentinel — never `$0.00`, which would read as free).
- **Capability-driven effort**: `Effort` is one shared union (`src/types.ts`): `'low' | 'medium' | 'high' | 'xhigh' | 'max'` (`providers.ts` and `usePersonas.ts` both re-export it rather than each declaring their own copy, as before this feature). `xhigh` sits between `high` and `max` and is Anthropic's recommended default for coding/agentic work on Opus 5/Sonnet 5/Fable 5. Which levels a given model actually accepts is derived from the live `capabilities.effort.<level>.supported` tree (`mapCapabilities()` in `registry.ts`) into `ModelCapabilities.effortLevels` — never a name-prefix guess. `EffortPill` only offers the levels the *currently selected model* supports (its `levels` prop). `selectedEffort` is model-independent React state and is **not** reset on a model switch; `clampEffort()` (`ChatInputArea.tsx`) only clamps what the pill *displays*, and the server strips an unsupported level in `createProvider()` before it reaches Anthropic. Adaptive thinking is gated the same way (audit C7): `providerOptions.anthropic.thinking` is attached only when the model's capabilities report `supportsThinking` (live `capabilities.thinking.types.adaptive.supported`), so Haiku 4.5 and an unknown id get neither thinking nor effort.
- **Persona tiers** (`src/hooks/usePersonas.ts`) — see `docs/PERSONAS.md` for the user-facing roster. 13 of the 14 built-in personas set `model` to a `ModelTier` (`'flagship' | 'opus' | 'sonnet' | 'haiku'`, `src/lib/models/types.ts`) instead of an exact id, so they auto-adopt Anthropic's newest release in that family. `tierFamily(tier)` maps `'flagship'` → the `fable` family (the one irregular mapping) and every other tier to its same-named family — a single pure helper shared by the server-only `resolveTier()` (`registry.ts`) and the client `resolvePersonaModel()`/`resolvePersonaModelLabel()` so the semantics can't drift between the two copies. **Persona resolution is client-side**, against the `models` list `page.tsx` already fetches from `GET /api/models` — `resolveTier()` reads API keys via `@/lib/settings` and is server-only, never imported into the `'use client'` hook. Its live server callers are the artifact regenerate route (`REGEN_TIER`) and `resolveRequestedModel()`'s defensive tier backstop. `resolvePersonaModelLabel()` prefers the matched row's real `name` over a static id→label map, so a dated-only id still renders a clean display name ("Claude Haiku 4.5"), never the raw "haiku-4-5-20251001". **Contract Abstract stays pinned to the exact `claude-fable-5`** — its locked 22-field extraction schema must not shift under a silent tier-following model swap.
- **Cost capture** (spec §C6) — `src/lib/usage.ts`'s `recordUsage()` writes one best-effort `usage_events` row (see Database section for the column shape; migration `0018`, **applied to Supabase 2026-09-11**) per LLM generation, called from **every LLM call site**: `POST /api/chat` (`purpose: 'chat'`, `totalUsage` summed across the whole tool-call loop), `POST /api/artifacts/[id]/regenerate` (`'artifact-regenerate'` — real Claude spend, not free housekeeping), the four Gemini Flash housekeeping routes (`summarize`, `generate-title`, `classify`, `memory-suggest`), and (audit C5, migration `0023`) `POST /api/suggest-followups` (`'suggest-followups'`, unattributed — the request carries no chat id), the retrieval stages `rewriteQuery()` (`'query-rewrite'`) and `rerankCandidates()` (`'rerank'`, one row per call, up to two per turn), both billed to the chat via `retrieveContext()`'s scope, `generateImageBytes()` (`'image-generate'` — both `POST /api/images/generate` and the chat's `generate_image` tool; Nano Banana is per-image so its rows carry tokens at cost 0, estimated), and `visionExtraction.ts` (`'vision-extract'`, one row per completed segment or image call, unattributed). A call that throws (abort, timeout, provider error) records nothing. `'classify'` stays in `UsagePurpose` and the CHECK for the rows already stored under it. Every call site is `void recordUsage({...}).catch(() => {})` — a usage-write failure never fails the request that generated the tokens. In `/api/chat` the write goes through `after()` from `next/server` (fire-and-forget fallback outside a request scope), `streamText` gets `abortSignal: req.signal` + an `onAbort` that records the completed steps via `sumUsage()`, and `result.consumeStream()` drains the stream server-side — so a Stop, tab close, or mid-stream provider error still yields exactly one usage row and cancels the upstream generation. A per-request first-wins guard keeps it to exactly one row even though the SDK fires both `onAbort` and `onFinish` on a mid-tool-loop abort, and no row is written when tokens are unknown (abort before any step completed).
- ⚠️ **Cache-token accounting** — settled by reading the *installed* `@ai-sdk/anthropic@3.0.98` source (`dist/index.mjs`), not public docs, which mix SDK versions: `usage.inputTokens` is the SDK's **inclusive** sum of fresh + cache-read + cache-write input, even though Anthropic's own API reports the three as mutually exclusive. A naive `inputTokens × rate + cacheRead × 0.1 × rate + cacheWrite × 1.25 × rate` formula **double-counts every cached token**, worst on exactly the long-context project chats this app targets. `usageTokens()` (`usage.ts`) derives the fresh count from `usage.inputTokenDetails.noCacheTokens` directly (falling back to `inputTokens - cacheRead - cacheWrite` only if that field is absent — `usage.inputTokens` is never used raw); `usage.cachedInputTokens` is deprecated in this SDK version and never read. `estimateCost()` applies the cache rates (read: the model's own `cacheReadPerMTok`, else ×0.1 of input; write ×1.25 of input) to the correctly-split counts.
- **Settings → Usage tab** (`UsageSettingsTab.tsx`, in `SettingsDialog.tsx`) shows monthly spend by model for the trailing 3 months (`getMonthlyUsageByModel()` in `actions.ts`, bucketed `AT TIME ZONE 'UTC'` before `to_char` so the grouping is independent of the Postgres session's timezone) — a per-model thin bar list per month, reusing the `ProjectDefaultsDialog` bar idiom but with a trailing dollar figure instead of a percentage. An always-unpriced row (the `gemini-3.5-flash` housekeeping sentinel: `cost_usd=0, cost_estimated=true`) renders as **"unpriced,"** never "$0.00" (`isUnpricedUsage()` in `utils.ts`) — that tuple is otherwise indistinguishable from a genuine free Claude generation and would misleadingly read as "free." `formatUsd()` (`utils.ts`) shows up to 8 decimals for sub-cent costs (matching `cost_usd`'s own `numeric(12,8)` scale) so a real $0.00003 charge is never rounded away to the same "$0.00" a `toFixed(2)` would give it. Per-chat spend surfaces in `ChatContextMenu` ("Cost: $X.XX", lazily fetched via `getChatCost(chatId)` only when the menu opens — not on every sidebar render) — `getChatCost` sums every `usage_events` row tied to the chat (all purposes, not just chat turns) and excludes `cost_usd=0` rows from its `estimated` flag so a chat that only ever triggered free housekeeping (nearly every chat, via `generate-title`) doesn't misreport "(est.)" on a genuine $0 figure. `ChatContextMenu`'s `@/app/actions` import is **dynamic**, not static — a static import pulls `@/db` into jsdom test renders that don't mock it and throws on a missing `DATABASE_URL`; `UsageSettingsTab.tsx` has the identical hazard via a static import and is only latent because no test currently renders `SettingsDialog` (a shared `@/db` test mock is a queued follow-up, not built here).
