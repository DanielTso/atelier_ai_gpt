# Database schema reference

_Moved word for word from the root `CLAUDE.md` on 2026-11-12 so it loads only when needed. `CLAUDE.md` links here; keep this file current whenever this area changes._

- Schema at `src/db/schema.ts` (`pg-core`): integer PKs via `GENERATED ALWAYS AS IDENTITY`, `timestamptz`, `boolean`, FK cascade deletes enforced natively (no `PRAGMA`). Tables: `projects` → `chats` → `messages`, `settings`, `messageEmbeddings`, `documents`, `documentChunks`, `documentRevisions`, `messageAttachments`, `personaUsage`, `artifacts`, `artifactVersions`, `memorySuggestions`, `generatedImages`. `projects` carries `memory`, `instructions`, and `updated_at` columns.
- **Moving a chat re-tags its children** — `moveChatToProject` updates `project_id` on `chats`, `artifacts`, `message_embeddings`, `persona_usage` and `usage_events` (where `chat_id` matches) in one transaction (audit B2). Without it the moved chat's history stays scoped to the old project, and deleting that project cascades the artifacts, embeddings and persona usage away. `recordPersonaUsage` likewise takes the project from the chat row, not the caller.
- **`memorySuggestions` table** — `id, project_id, chat_id, text, status (pending|accepted|dismissed), created_at` + index on `(project_id, status)`. Added by migration `drizzle/0008_busy_miss_america.sql`. `chat_id` is **SET NULL** on chat delete (project-level suggestions survive). Rows are auto-memory candidates created by `POST /api/memory/suggest`; accepting one appends to `projects.memory`.
- **pgvector**: `messageEmbeddings.embedding` and `documentChunks.embedding` are `vector(768)` with **HNSW** indexes (`vector_cosine_ops`). The `vector` extension is enabled by migration `drizzle/0000_enable_vector.sql`.
- **`documents.extraction_method`** — text column (`'text'` | `'vision'` | `'hybrid'`), nullable; added by migration `drizzle/0004_sudden_ben_grimm.sql`. Set by `/api/documents/process`; surfaced in `GET /api/documents` and displayed as a badge in `DocumentCard`.
- **`documents.failed_pages`** — `jsonb`, nullable (array of absolute page numbers, `null` when none); added by migration `drizzle/0015_chemical_sugar_man.sql`. Written from `extractViaVision`/`extractPagesViaVision`: every page vision did not extract, i.e. the pages of a segment that fails after retries, a page skipped as oversize, and (whole-doc vision path) pages past `EXTRACTION_MAX_PAGES`, sorted and deduped (audit X9/K28; before that, skipped pages were only counted and capped pages were not recorded). The hybrid path's `EXTRACTION_HYBRID_MAX_PAGES` cap is not recorded, since those pages keep their text layer. Plumbed through `/api/documents/process` → `GET /api/documents` (`failedPages`) → `DocumentCard`'s Partial badge tooltip (`formatPageList` in `src/lib/utils.ts` renders run-length ranges, e.g. "12–14, 30") and to `read_document`'s `unavailablePages`. No backfill — existing docs gain it on re-upload.
- **`artifacts` table** — `id, chat_id, project_id, type, title, storage_path, status, error_message, created_at` + index on `chat_id`. Added by migration `drizzle/0005_lyrical_onslaught.sql` (applied to live Supabase). Rows are created by the `generate_artifact` tool during a Claude chat turn and read back by `GET /api/artifacts?chatId=`.
- **`document_chunks.content_tsv`** — generated `tsvector` column (`GENERATED ALWAYS AS (to_tsvector('english', content)) STORED`) + GIN index `idx_chunks_tsv`, plus a GIN trigram index `idx_chunks_trgm` on `document_chunks.content` (`pg_trgm` extension). Raw-SQL migration `drizzle/0016_hybrid_search.sql` — **not represented in `src/db/schema.ts`** (Drizzle doesn't model generated columns); backs `findChunksByKeyword` (`src/lib/keywordSearch.ts`), the keyword leg of hybrid retrieval (see Context Pipeline).
- **`document_chunks` unique `(document_id, chunk_index)`** — unique index `uq_chunks_document_chunk`, migration `drizzle/0022_unique_document_chunk_index.sql` (**authored, not yet applied to Supabase** — the owner applies it at release, before the code that relies on it deploys). One row per chunk position, so a second ingest of the same document can never add a duplicate chunk set (audit D2: two concurrent ingests used to leave 12 rows with `chunk_count` 6). Production may already hold such duplicates, so the migration first takes `LOCK TABLE document_chunks IN SHARE ROW EXCLUSIVE MODE` (blocks chunk writes by a concurrent old-code ingest until the index exists; reads continue), then sets `documents.chunk_count` to the distinct chunk count for every document that has duplicates, then deletes the extras — keeping one row per pair, a row with an embedding over one without, then the lowest `id` — and only then creates the index; documents without duplicates are untouched. Tested in PGlite by migrating to `0021`, seeding duplicates and applying `0022` (`tests/unit/db/migration-0022.test.ts`). The generated part of the migration is only the `CREATE UNIQUE INDEX`; it does not touch `content_tsv` or the `0016` GIN indexes. The older non-unique `idx_chunks_document_id` stays (now redundant with the unique index's leading column).
- **Document ingest is one transaction** — `commitDocumentIngest` (new upload / web ingest, via `ingestText`) and `commitDocumentReplacement` (replace) each take `SELECT … FOR UPDATE` on the document row first (one lock order, so they cannot deadlock), then swap the document's chunk set and write its status/metadata in a single transaction, with embeddings computed **before** it opens (no transaction held across provider calls). Chunk rows are inserted in slices of 500. `claimDocumentForProcessing` is the only way `/api/documents/process` enters `processing`: `UPDATE … SET status='processing' WHERE id=$1 AND status=$expected AND revision=$expected AND status IN ('uploading','ready','error') RETURNING` — a compare-and-set against the row the route read, so a concurrent call, or a request whose snapshot went stale because another replace committed in between, gets nothing back and is refused (409).
- **`document_chunks.page_start` / `page_end`** — nullable ints, migration `drizzle/0017_clumsy_demogoblin.sql` (**applied to Supabase**). Stamped at ingest from `# Page n` anchors via `src/lib/pageMap.ts` + the offset-bearing `chunkText`. Vision docs carry an anchor per page (prompted, and `visionRunText` adds the first page's when the model omits it); hybrid docs carry one on every page, text-path pages included (`spliceHybridPages`, audit X1). Null for text-path docs (no anchors) and all pre-0017 chunks. Hybrid docs ingested before the X1 fix have anchors only inside their vision runs, so their stored values are wrong (a 40-page set with one run on page 4 has every chunk `{4,4}`). No backfill — re-upload (replace) gains or corrects them. Feeds citation source headers and chip page targets.
- **`usage_events` purpose CHECK covers every LLM call site** — migration `drizzle/0023_usage_purpose_llm_sites.sql` (**authored, not yet applied to Supabase** — the owner applies it at release, **before** the code that writes the new purposes deploys; until then those writes fail the CHECK, `recordUsage()` swallows the error with a warn, and the rows are simply missing — the requests themselves are unaffected). Drops and re-adds `usage_events_purpose_chk` with the five purposes of audit C5 (`suggest-followups`, `query-rewrite`, `rerank`, `image-generate`, `vision-extract`) added to the six it already allowed. **Every existing value stays allowed** — the re-added CHECK is validated against all stored rows, and production holds rows for each old purpose, `'classify'` included (it outlives `/api/classify`). Generated by `drizzle-kit generate`; touches no other object (`content_tsv` and the `0016` GIN indexes untouched). Tested in PGlite by migrating to `0022`, seeding one row per existing purpose, then applying `0023` (`tests/unit/db/migration-0023.test.ts`): the rows survive, the new purposes are accepted, and an unknown one is still rejected.
- **`chat_topics` table dropped** — migration `drizzle/0024_drop_chat_topics.sql` (**authored, not yet applied to Supabase** — the owner applies it at release). Its only writer, `POST /api/classify`, is gone, so the migration is `DROP TABLE "chat_topics" CASCADE` and nothing else (`content_tsv` and the `0016` GIN indexes untouched; `drizzle-kit generate` afterwards reports no schema changes). `'classify'` stays in `UsagePurpose` and the `usage_events_purpose_chk` CHECK for stored rows. Tested in PGlite (`tests/unit/db/migration-0024.test.ts`): migrate to `0023`, table exists, apply the real `drizzle/`, table gone, `'classify'` usage rows still insert.
- **`usage_events` table** (Dynamic Model Registry + Cost Visibility, spec §C6) — `id, chat_id, project_id, purpose, model, input_tokens, output_tokens, cache_read_tokens, cache_creation_tokens, cost_usd numeric(12,8), cost_estimated, created_at` + indexes on `chat_id`, `(model, created_at)`, `created_at`, `project_id` and CHECKs `usage_events_purpose_chk` / `usage_events_tokens_nonneg_chk` (migration `0019`; the purpose CHECK is replaced by `0023`, below). Migration `drizzle/0018_dapper_morg.sql` (**applied to Supabase 2026-09-11**, together with `0019` indexes/CHECKs). One best-effort row per LLM generation, written by `recordUsage()` (`src/lib/usage.ts`) from every LLM call site: chat, artifact-regenerate, summarize, generate-title, classify, memory-suggest, and — once `0023` is applied — suggest-followups, query-rewrite, rerank, image-generate, vision-extract. `input_tokens` stores **FRESH (non-cached) input only** — NOT the AI SDK's inclusive `usage.inputTokens` (see Model Registry & Cost Visibility below) — so the three input columns are mutually exclusive and rollups can `SUM()` them without double-counting. `cost_usd` is computed and **frozen at write time**; a later price change never reprices history. `cost_estimated: true` means the price was inferred from a family tier, not that the model is free. `chat_id`/`project_id` are `ON DELETE SET NULL` (not cascade) — a usage row is a billing record, so spend history survives chat/project deletion.
