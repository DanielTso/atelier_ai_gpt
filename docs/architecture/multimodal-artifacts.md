### Multimodal

**Input**: Images sent as `FileUIPart` via `sendMessage({ text, files })`, persisted in `message_attachments` table, reloaded as `file` parts on page load. The attachment rows are written by the client's turn pipeline (`useChatPersistence`) as soon as `/api/chat` reports the saved user row's id — on the stream's first chunk, before the reply. `convertToModelMessages()` handles format conversion automatically. Gemini has vision support. **Chat image rules (audit U4/U11):** only `image/png|jpeg|webp|gif` are accepted — the types Claude reads (a file with an empty MIME type is typed from its extension for these four); SVG/HEIC/AVIF and other image formats are refused with "Unsupported image type" (a persisted unreadable image would fail every later turn in the chat). Images over 1 MB are downscaled in the browser (`src/lib/imageDownscale.ts`: long edge ≤ 2048 px, WebP q≈0.85, JPEG where WebP encoding is unavailable; GIFs are left as-is so animations survive). Because images travel as base64 inside the `/api/chat` JSON body (Vercel caps request bodies at 4.5 MB), the combined data-URL payload is capped at `CHAT_IMAGE_BUDGET_BYTES` (3 MB, `src/lib/fileAttachments.ts`): an image that would exceed it is refused at attach time and the send is refused with "Images too large to send together (max 3 MB)". **Whole-request guard:** every `/api/chat` request carries the session's WHOLE transcript (earlier inline images, attached files' text, tool outputs), so each send is also measured as the real outgoing body — target session's messages + the new message, UTF-8 bytes — against `CHAT_REQUEST_BUDGET_BYTES` (4 MB, `src/lib/chatRequestSize.ts`) and refused with a size-specific toast ("This message is too large…" / "This chat's attachments are too large to send in one request — start a new chat to continue") instead of hitting the platform's generic 413. **Inline images are swapped out after saving:** `saveMessageAttachments` returns each Storage-backed row with a signed URL (24 h TTL, input order), and the turn pipeline replaces that turn's data-URL file parts in the live session with those URLs (`replaceFilePartUrls`) — the same shape `loadMessages` rebuilds after a refresh — so earlier images stop counting against later request bodies. Without Storage the data URLs stay and the guard is the backstop. A failed `saveMessageAttachments` shows a toast (the images would otherwise vanish on refresh unannounced). **Non-image chat attachments** are text-extracted, not sent as files: browser → signed Storage upload → `POST /api/extract { storagePath }` (see data-flow.md); send (button and Enter) stays disabled while any attachment is still being extracted or downscaled, and attachment state is updated functionally so concurrent drops keep every file.

**Document surfaces (Phase C3)**: Both `ProjectDocumentsDialog` (modal) and `ProjectLandingPage` (Files panel) render a `DocumentCard` grid and use `useDocumentUpload` for uploads. Both now accept images (png/jpg/jpeg/webp) in addition to PDF/DOCX/XLSX. Clicking a card opens `DocumentPreviewDialog` (tabbed: "Preview" renders originals inline; "Extracted text" reconstructs chunks). The `vision` badge on a card indicates the document was processed via Gemini vision extraction (vs. text extraction). **Phase C is complete (C2 + C-storage + C3).**

**Attachment persistence (Phase C-storage Stage 2)**: `saveMessageAttachments` uses a **dual-write** strategy — when Storage is configured (`isStorageConfigured()`), it decodes the base64 data URL, uploads bytes to `attachments/<chatId>/<messageId>/<i>-<filename>` in the private Supabase Storage bucket, and stores `storage_path` with `data_url` null. When Storage is NOT configured, it falls back to storing the base64 `data_url` in the DB column (graceful degradation — unlike documents, chat attachments keep working with no Storage configured). `message_attachments.storage_path` is nullable; `data_url` is also nullable (one or the other is populated). `getChatAttachments` does a **dual-read**: rows with `storage_path` get a short-lived signed URL via `createSignedDownloadUrl`; legacy `data_url` rows are returned unchanged. No backfill of old rows. `deleteChat` / `deleteMessage` remove relevant Storage objects best-effort before the DB cascade. Migration `drizzle/0003_superb_roughhouse.sql` added `storage_path` + made `data_url` nullable. Known deferral: deleting a whole **project** does not sweep attachment Storage objects (consistent with the Stage 1 orphan-sweep deferral).

**Output (Nano Banana 2)**: Gemini image models (`gemini-3.1-flash-image`) return generated images as `file` parts in assistant messages. The turn pipeline (`useChatPersistence`, at turn end) extracts these `file` parts and persists them to `messageAttachments` (same table as user-attached images), keyed to the assistant row `/api/chat` saved (id from the turn metadata). Both user-attached and AI-generated images render inline in `MessagesList` with a click-to-expand lightbox overlay (Framer Motion animated, fullscreen with backdrop blur). Generated images display at 512px; user images at 300px.

**Artifacts**: Claude can generate **brand-styled** file artifacts — **XLSX, DOCX, PDF, PPTX** (downloadable) and **HTML** (live preview) — via the `generate_artifact` tool (pure-JS renderers: `exceljs`, `docx`, `pdf-lib`, `pptxgenjs`; HTML passes through). The tool is **chat-first** (only fires on an explicit file/web-page request — see `TOOL_GUIDANCE`). `page.tsx` fetches artifacts from `GET /api/artifacts?chatId=` on chat open and re-fetches after each response; `ArtifactCard` renders below the assistant message; clicking opens **`ArtifactWorkspace`** — a right-side panel with **Preview / Edit / Versions** tabs, **Download**, and AI **regenerate** (`POST /api/artifacts/[id]/{edit,regenerate}`). Regenerate runs on the newest Sonnet in the live registry (`resolveRequestedModel('sonnet')`) with the chat route's output cap (`ARTIFACT_MAX_OUTPUT_TOKENS`, 32k; `maxDuration` 800 s); output that stops at the cap (`finishReason === 'length'`) is a `422` with no upload and no new version, and regenerated sheets that are not `{name, rows}` objects are a `422` too (audit B6/B14). Preview is live: PDFs via the **same-origin proxy** (`<iframe src="/api/artifacts/:id/raw">` — NOT the cross-origin signed URL, which browsers block in an iframe), HTML in a sandboxed `<iframe srcDoc>` (`sandbox="allow-scripts"`, no same-origin), sheets→table, markdown→HTML. The workspace panel is **resizable** (drag its left edge; width clamped 360px..80vw and persisted in `artifact-panel-width`); dragging it wide enough to cramp the chat **auto-collapses the sidebar** (and restores it on narrow/close, only if it auto-collapsed). Source `content`/`format` + an `artifact_versions` table back preview/edit/versioning. **Inline images** are separate: the `generate_image` tool (`src/lib/image/tool.ts`) makes Claude produce images inline via Nano Banana (see provider routing). Migrations: `0005` (artifacts), `0010` (artifact_versions). Deps: `docx`, `pdf-lib`, `pptxgenjs`, `marked`.
