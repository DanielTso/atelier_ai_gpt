# Data flow and API routes

_Moved word for word from the root `CLAUDE.md` on 2026-11-12 so it loads only when needed. `CLAUDE.md` links here; keep this file current whenever this area changes._

### Data Flow

1. **Client** (`src/app/page.tsx`) — Single-page chat UI on the AI SDK's `Chat`/`useChat` (`@ai-sdk/react`), **one chat session per DB chat** (`src/hooks/useChatSessions.ts` — see "Chat turns" below). All application state lives here. A top-level `activeView` state (`AppView` = `home | projects | artifacts | images`) is driven by the left `SidebarNav` (New chat · Projects · Artifacts · Images · Customize/Settings) and swaps the main pane: **`home`** = the chat surface (active chat, project landing page, or the branded empty/home state with an always-visible input toolbar), **`projects`** = all-projects grid, **`artifacts`** = artifact gallery, **`images`** = the Images studio. Sending a message with no active chat auto-creates a standalone quick chat.
2. **Server Actions** (`src/app/actions.ts`) — "use server" functions for all DB reads/writes (CRUD for projects, chats, messages, settings, chat previews). Exception: chat-turn message text is written by `POST /api/chat`, not by a client-called action.
3. **API Routes**:
   - `POST /api/chat` — Streams LLM responses. Claude models (`claude-*`) route to Anthropic with **web search** enabled (`anthropic.tools.webSearch_20250305`). The Gemini image model (`*image*`) gets `responseModalities: ['TEXT', 'IMAGE']`. Applies five-layer context (see below). Default model fallback is `claude-opus-4-8`. For Claude project chats with ≥1 `ready` document, also wires the **`read_document`** tool (whole-document mode — see Context Pipeline) plus a `[Project documents]` manifest and `READ_DOCUMENT_GUIDANCE` in the system prompt. **Persists the turn** to the request's `chatId` and reports the row ids as message metadata — see "Chat turns" below. An unknown `chatId` is a `404` with nothing written. A **regenerate** (`regenerate: true` + `replaceMessageDbId`) replaces the chat's last reply: `400` when malformed, `409` when that reply is no longer the newest message (see "Chat turns"). A provider failure mid-stream reaches the client as a fixed, specific error message per class — bad key (401/403), rate limit (429), out of credits, context too large (413, or a 400 "prompt is too long"), Fable's data-retention requirement, other 400, overloaded (529/5xx) — and the provider's raw text is only logged server-side (`providerErrorMessage` in the route).
   - `GET /api/models` — Thin wire-shape adapter over the **dynamic model registry** (`src/lib/models/registry.ts`, `getModelRegistry()` — see Model Registry & Cost Visibility below): serves the live Anthropic catalog, curated to one newest entry per family (Opus first → the default; then Fable, Sonnet, Haiku), plus Nano Banana 2 when the Gemini key is set. Key-gated (no Anthropic key ⇒ no Claude entries) and never empty (degrades to a static seed on any fetch failure). `Cache-Control: public, max-age=300`; the registry itself is cached in-process with its own shorter TTL when degraded. After a Settings save (API keys or model defaults) the page re-fetches with `fetch('/api/models', { cache: 'reload' })`, which bypasses that browser cache and re-primes it, so newly configured models appear at once (audit U8).
   - `POST /api/summarize` — Compresses older messages. Auto-triggers at 30+ messages, keeps last 10 in full. Pinned to internal `gemini-3.5-flash` (housekeeping never burns Claude tokens). An empty or blocked model reply is a `502` that leaves the existing summary and its `summaryUpToMessageId` untouched (audit B22); the client's fold gate (`useChatPersistence`) is rolled back on any non-2xx or network error, so the fold is retried after `SUMMARIZE_RETRY_AFTER` (4) more messages, about two turns (audit B4).
   - `POST /api/embed` — Async 768-dim embedding generation via Gemini `gemini-embedding-001`. Best-effort, per message (called from the client's turn pipeline with the row ids `/api/chat` reported: the user's message at turn start, the reply at turn end). The embedding's `project_id` is the chat's DB project, looked up from `chatId`; a body `projectId` is ignored (still accepted for one release), and an unknown `chatId` is a 404 (audit U3). Only the first `EMBED_MAX_CHARS` (default 8,000, `src/lib/embedChunks.ts`) are embedded and stored; the body's `content` is capped at 500k chars by the schema. An embedding failure is a sanitized `502` (it used to be a 200 the client ignored, audit B13). A malformed JSON body is a `400`, and no configured embedding provider is a `503 { success: false }`. A message whose embed failed has no `message_embeddings` row. The operator script `scripts/backfill-embeddings.ts` (`npx -y tsx --env-file=.env.local scripts/backfill-embeddings.ts [--since <ISO>] [--limit <N>] [--dry-run]`, logic in `src/lib/embeddingBackfill.ts`) embeds such messages oldest first. It is idempotent, `--limit` is 1–1000 (default 200), and it returns `{ embedded, failed, skipped, remaining }`. `skipped` counts rows never attempted because the provider failed 5 times in a row and the run stopped. `--dry-run` only counts `remaining`. It is deliberately not a server action, so it is not a network endpoint. It calls Gemini, so running it against production is an owner-approved step.
   - `POST /api/generate-title` — Auto-generates chat title (3-6 words) after first AI response. Pinned to internal `gemini-3.5-flash`.
   - `POST /api/extract` — Extracts text from chat attachments (PDF via `unpdf`, DOCX via `mammoth`, XLSX via `exceljs` — one tab-separated block per sheet, text/code via UTF-8). Max 200MB (`MAX_FILE_SIZE`; large construction plans). Two body shapes: **JSON `{ chatId, storagePath, mediaType? }`** (the normal path) extracts from an object the browser uploaded straight to Storage, so the file never crosses Vercel's 4.5 MB request-body limit; the path must be one `<uuid>-<name>` segment under the chat's own `attachments/<chatId>/pending/` prefix (`attachments/compose/pending/` while composing a chat that doesn't exist yet; `src/lib/attachmentPaths.ts`), anything else is a 400 before Storage is touched, and the object is deleted after extraction (the text travels in the message). **Multipart `file`** stays as the fallback when Storage is unavailable, and the client only uses it for files ≤ 4 MB (larger ones get a size-specific message instead of a doomed request; when Storage IS configured but the signed upload itself fails, a file over 4 MB gets "Couldn't upload <name>: <reason>" instead). Returned text is capped at `CHAT_ATTACHMENT_MAX_CHARS` (500k chars, `fileExtraction.ts`; flagged `truncated`) — it is inlined into the message and re-sent in every later `/api/chat` body — and the route sets `maxDuration = 300` for large-PDF extraction. A pending object whose extract call never arrives (tab closed after upload) is swept later (audit R4, `src/lib/attachmentSweep.ts`): the next `POST /api/attachments/upload-url` for the same scope (that chat, or `compose`) removes, after its response, the scope's `pending/` objects older than 1 hour (`PENDING_ATTACHMENT_MAX_AGE_MS`), and `deleteChat` removes all of that chat's `pending/` objects. Both are best-effort and never fail the request.
   - `POST /api/attachments/upload-url` `{ chatId, filename, mediaType, size }` → `{ path, token, bucket }` — step 1 of the chat-attachment flow above: validates size (≤ `MAX_FILE_SIZE`) and type (text-extractable only; images go inline with the message), then mints a signed upload for `attachments/<chatId|compose>/pending/<uuid>-<sanitized name>`. 503 when Storage isn't configured. Client side lives in `src/lib/attachmentExtract.ts` (upload-url → `uploadToSignedUrl` → extract; error bodies read through the shared `readError`, which turns a non-JSON platform 413 into "File too large for upload"). **Supabase Storage must also allow the size:** the org is on the **Pro** plan, the `atelier-files` bucket `file_size_limit` is set to 200MB, and the **project-global Storage upload limit** (Supabase dashboard → Project Settings → Storage) must be ≥ 200MB or large signed uploads are rejected server-side.
   - **Document upload — 3-step direct-to-Storage flow (Phase C-storage):**
     - `POST /api/documents/upload-url` — validates name/type/size, creates a `documents` row with status `uploading`, returns `{ documentId, path, token, bucket }` for the browser. The path needs the row id, so the row is inserted first; if setting the path or signing the URL fails, the row is deleted (no `uploading` orphan for the reaper, audit B25). **Replace** (`replaceDocumentId`) signs `documents/<project>/<doc>/rev<N+1>/<name>` (upsert) and does **not** change the document's status (audit X7): the previous revision stays `ready`, listed and retrievable while the browser uploads, so an abandoned replace changes nothing.
     - Browser calls `uploadToSignedUrl` (`src/lib/storageClient.ts`, anon key) to PUT the file straight to Supabase Storage, bypassing the Vercel function request-body limit (large plans work).
     - `POST /api/documents/process` `{ documentId }` — downloads original from Storage, runs the C2 extract pipeline (text / thin-PDF vision fallback / image vision), uploads a WebP thumbnail, chunks + embeds, records `extraction_method` (`'text'` or `'vision'`), sets status `processing` → `ready | error`. The old inline `POST /api/documents` + `createDocument` action are retired. The embed pool (`embedContents`) stops after `EMBED_FAIL_FAST_AFTER` (default 5) consecutive failures and counts the rest as failed, so a full Gemini outage fails the document fast instead of running into the platform kill (audit B11). A new upload whose chunks all fail is `error` with an `error_message`; reaching `ready` clears any stale `error_message` (audit B21). **Claim (audit D2):** the route enters `processing` only through `claimDocumentForProcessing` (`status IN ('uploading','ready','error')`), a compare-and-set on the status and `revision` it read; a document read as `processing`, a second call while one is running, or a stale snapshot (another replace committed in between, so the derived `rev<N+1>` paths would be the live revision's) gets **409** and touches nothing. The new-upload tail (`ingestText`) embeds every chunk first, then swaps the chunk set and writes the status in one transaction (`commitDocumentIngest`, row-locked; unique `(document_id, chunk_index)` from migration `0022`), so a repeat or concurrent ingest can never leave two chunk sets or a `chunk_count` that disagrees with the rows. **Every exit after the claim leaves a settled status (audit B8, X8):** the whole tail is wrapped, so a throw no longer leaves `processing` for the 20-minute reaper. A failed first upload is `error` with an `error_message`. A failed **replace** — no embedding provider (503), download failure (500), extractor throw (500), no text (400), a TOTAL embed failure or the pool stopping early (502), or any throw before the commit — leaves the document with the status it had before the request (`ready` stays `ready`, `error` stays `error`, audit B25; a row an older deploy left `uploading` falls back to `ready` if it had chunks, else `error`), and the previous revision's chunk index is never touched. **Replace path (v4.51.0):** embeds BEFORE any destructive write, then snapshots the old revision and commits atomically. A failed replace also removes the `rev<N>` objects of the revision it was building — the uploaded file, `thumb.webp`, `extracted.txt` (audit X12; best-effort, never while the commit's outcome is unknown); a retry uploads them again.
   - `GET /api/documents` — returns each doc with short-lived signed `url` (original) + `thumbnailUrl` (best-effort, `null` if absent) + `extractionMethod` (`'text'` or `'vision'`). `DELETE /api/documents` — removes Storage objects (original + thumbnail) before deleting the DB row.
   - **Web ingestion — "Add from web" (Design B, v4.32.0):** `POST /api/documents/web-map` `{ url, maxDepth?, limit? }` → Tavily site map (`{ urls, configured }`, key-guarded); `POST /api/documents/web-ingest` `{ url, projectId }` → Tavily Extract → markdown → creates a `text/markdown` `documents` row (filename = the page's first `#` heading passed through `promptSafeLabel()` (`src/lib/promptSafe.ts`), falling back to `<host><path>` when that is empty — the filename reaches the system prompt; a `Source: <url>` header is prepended so provenance carries into chunks) → uploads `source.md` to Storage → runs the **shared `ingestText` tail** (chunk→embed→status). Status codes: 422 empty / 502 upstream Tavily failure / 503 no-key|storage|embeddings. The Tavily key is **server-only** (`getTavilyApiKey`, in `SENSITIVE_KEYS`, never returned/logged). Client orchestrates per-page via `useWebIngest`; UI is `AddFromWebDialog` (opened from the Files rail "Web" button + the Documents dialog).
   - **Removed (audit D3):** `POST /api/classify` and the `chat_topics` table (migration `0024`). `'classify'` stays a valid `usage_events` purpose for stored rows. `/api/summarize` and `/api/generate-title` no longer declare a `model` field (a stray one is stripped); both are pinned to `gemini-3.5-flash`.
   - `POST /api/memory/suggest` — **auto-memory** (suggest, you approve). Throttled best-effort pass (Gemini `gemini-3.5-flash`, never Claude tokens) that extracts durable project facts and stores them as pending `memorySuggestions`. Key-guarded (`{ created: 0 }` with no key), cap-gated at ~10 pending (`{ created: 0, capped: true }`, no model call), dedups against current `projects.memory` + pending + recently-dismissed. Triggered every 6 messages in a **project** chat from the turn pipeline (`useChatPersistence`, at turn end), filed on the chat's DB project, looked up server-side from the required `chatId` (a body `projectId` is ignored; a standalone chat returns `{ created: 0 }`, an unknown chat 404s — audit U3); reviewed via the "Suggested memories" strip in `ProjectContextRail` (Accept appends to `projects.memory` and reports the new value to the page through `onMemoryChanged`, so the page's project state — which the rail remounts from — never holds the pre-accept text (audit U6); Edit, Dismiss). Never surfaces as a user error. Actions: `createMemorySuggestions`, `getPendingSuggestions`, `countPendingSuggestions`, `getRecentlyDismissed`, `acceptSuggestion(id, overrideText?)`, `dismissSuggestion`.
   - `GET /api/artifacts?chatId=` — returns all artifacts for a chat with short-lived signed `downloadUrl` per row. `DELETE /api/artifacts?id=` — removes the Storage object then the DB row.
   - `GET /api/artifacts/[id]/raw` — streams the artifact's stored file **same-origin** (`downloadToBuffer` → bytes, `Content-Type` by type, `Content-Disposition: inline`). The PDF preview embeds THIS, not the cross-origin Supabase signed URL — browsers increasingly block cross-origin PDFs in an `<iframe>` ("content is blocked"). Auth-gated by middleware. Pairs with the relaxed `X-Frame-Options: SAMEORIGIN` / CSP `frame-ancestors 'self'` (next.config) so the app can frame its own proxy.
   - **Images (Phase Images, v4.36.0):** `POST /api/images/generate` `{ prompt, aspectRatio?, projectId? }` — standalone Nano Banana 2 generation (no chat turn) → uploads to `images/<projectId|standalone>/<uuid>.<ext>` → inserts a `generated_images` row → returns `{ image }` (signed `url`). Guards: 400 invalid, 503 no Gemini key / no storage, 502 generation fail. Backed by the shared `src/lib/image/generate.ts` (`generateImageBytes`); actions `getGeneratedImages(projectId?)` / `deleteGeneratedImage(id)`; UI is the **Images** sidebar view (`ImagesView` — centered "Create images" hero + gallery, All/Standalone/per-project filter).

### Chat turns: who saves what, and to which chat

A turn is the user's message plus the assistant's reply. **`POST /api/chat` saves both rows, to the chat named in the request** (audit U1/F1/F3, 2026-11-12). The client never writes message text. This is what makes a reply land in the chat it was sent from even when the user has moved to another chat, another view, or closed the tab.

**Server (`src/app/api/chat/route.ts`, `src/lib/chatTurn.ts`):**

- The chat is loaded first; an unknown `chatId` returns `404` and writes nothing. A request with no `chatId` streams without persisting anything.
- **User message** — inserted before the model is called (concurrently with provider setup, so it adds no round-trip to time-to-first-token). Only the **last** message of the request is ever inserted, and only when its id is not already a DB row id (`isDbMessageId`: history loaded from the DB carries stringified `messages.id`s; `useChat`-generated ids are 16 random characters). Re-saving a loaded message on every open was the F3 duplicate.
- **Assistant message** — exactly one row, written by `createAssistantTurnRecorder`, a `streamText` `experimental_transform`. **The row is first written while the reply streams** (audit R2): as soon as the turn has savable content (non-blank text or media) it is inserted (`save`), and from then on it is **checkpointed** — its `content` rewritten in place (`updateAssistantReplyContent` in `src/lib/chatTurnDb.ts`, scoped to `id` + `chat_id` + `role = 'assistant'`; a row deleted meanwhile is left deleted) — on every `tool-input-start`, `tool-call` and `finish-step` part (text written before a long tool run, or before a tool input that streams for a long time such as an artifact page, does not wait for it), and on a text delta once 3 s have passed since the last write started. Checkpoints are never awaited (they add no latency to the stream), never overlap (one in flight → the next is dropped, and a later one carries the newer text), and are skipped when the text has not changed; a failed one is logged and the next one retries. Every rewrite is compare-and-set on the text the turn last wrote (`content = previous`): a turn whose row was replaced (another tab's regenerate took it over) or deleted stops writing — no further checkpoint, no final write — and reports `assistantMessageDbId: null`, so the client links no images or embedding to a row it no longer owns; a rejected rewrite (a DB error) is not that, and is retried. The final text lands at the stream's `finish` part, or at its `abort` part with the text streamed so far — this write waits for any in-flight checkpoint and rewrites the row only if the text changed; a flush hook and a post-drain call cover streams that end with neither. **So a turn whose function is killed mid-stream (the 300 s `maxDuration`, a crash, a deploy) keeps its text up to the last checkpoint**, and its row exists for `getAssistantReplyId` and generated-image linking. The text is every step's text deltas concatenated — the same string the client renders. A turn with no text and no media (`generate_image` / `generate_artifact` result, or a model-emitted file part) writes no row; a media-only turn writes its (empty-text) row at the first checkpoint. It is a transform rather than `onFinish`/`onAbort` code for two reasons verified against `ai@6.0.230`: the insert must complete **before** the `finish` chunk is forwarded (so the row id can ride on it), and `onAbort` is called un-awaited from upstream of the text deltas.
- The transform sits on the base stream that `result.consumeStream()` drains, so it runs to the end whether or not anyone is reading the response. The drain-then-persist promise is handed to **`after(promise)`** (`waitUntil`) so the function is not frozen before the write lands. (The usage row keeps the `after(callback)` form — it runs after the response closes, and nothing on the wire depends on it.)
- `abortSignal: req.signal` still cancels the upstream generation when the **connection** drops (Stop, tab close, network loss) — the partial reply is saved. On Vercel this depends on `supportsCancellation` for the route in `vercel.json` (cancellation is opt-in per path); the function is terminated on disconnect. The reply save survives because it is registered with `after()` inside the request; the usage row is written from a stream callback through `after()`, with a fire-and-forget fallback, and there is none at all for a turn stopped during its first step (only completed steps are summed, and an unknown spend is never written as a $0 row). Navigating inside the app does not drop the connection, so those turns run to completion.
- **Turn metadata** — `toUIMessageStreamResponse({ messageMetadata })` sends `{ chatId, projectId, userMessageDbId, assistantMessageDbId }` (`TurnMetadata`) on the `start` chunk and again on the `finish` chunk. On `start` the assistant id is usually `null` (a checkpoint can occasionally land before `start` is converted, so it is not guaranteed either way); on `finish` it is authoritative — the row's id, or `null` when the turn wrote no row (or its row was taken over or deleted, above). `projectId` is the chat row's project, never a client value. `userMessageDbId` is the user row the reply answers: the row this request inserted, or, on a regenerate, the existing row. It is `null` when an ordinary send inserted nothing (its last message was already a DB row).
- **Regenerate** (audit D2) — the request carries `trigger: 'regenerate-message'` (from the SDK), `regenerate: true` and `replaceMessageDbId` (the reply being replaced); any one of the three marks it a regenerate. Validation, before any model work: it needs a chat, `replaceMessageDbId` and a trailing user message (else `400`), and `getRegenerateTarget(chatId, replaceMessageDbId)` must confirm that row is the chat's **newest** message, is an assistant reply, and follows a user row — and, when the posted user message carries a DB id, that it is that row (else `409`, nothing written, no provider call). **Nothing is inserted for the user turn** — the trailing user message is already saved, even when it carries a client id because it was sent this session (the double-insert the Phase B review flagged); its existing row becomes `userMessageDbId`. **Nothing is deleted up front: the new reply replaces the old one in place, at the recorder's first write** (the first checkpoint, once savable content exists; later checkpoints and the final write only rewrite that row's content). For a regenerate the turn recorder's first write goes through `replaceAssistantReply(chatId, replaceMessageDbId, text)` (`src/lib/chatTurnDb.ts` — server-only, deliberately not a `'use server'` action, so it is not a browser endpoint) instead of inserting. In one transaction it drops the old reply's attachment rows and embedding and rewrites its `content` (`UPDATE … WHERE id AND chat_id AND role = 'assistant'`; `created_at` is untouched because `getChatMessages` orders by it); if no row matches (deleted meanwhile, e.g. by message Delete) it inserts a fresh assistant row. The old attachments' Storage objects are removed after the commit, best-effort, logging the paths — except a generated image that an artifact of the same chat still embeds, which is kept (audit R4, `pathsSafeToRemove`). So: a regenerate that fails, or is stopped before its first token, persists nothing and the old reply survives; a stop mid-stream replaces it with the partial text; a clean finish reports `assistantMessageDbId === replaceMessageDbId`; repeated regenerates keep one row; and `getAssistantReplyId` (the row right after the user row) stays unambiguous — it is the same row before and after. On the id path of semantic retrieval the replaced reply's id is added to `excludeMessageIds`, so its old answer's embedding cannot feed back into the regenerate prompt. **Usage:** a regenerate is its own request, so it writes at most one `usage_events` row of its own through the same first-wins guard (none when it is stopped during its first step); the replaced reply's row stays (those tokens were billed). Artifacts the replaced reply created are chat-scoped and stay.

**Client (`src/hooks/useChatSessions.ts`, `src/hooks/useChatPersistence.ts`, `page.tsx`):**

- **One `Chat` instance per DB chat**, held in a registry and handed to `useChat({ chat })` for the chat on screen. A stream can only write to the store of the chat that sent it. Switching chats **never calls `stop()`**; a reply left streaming keeps running in its own session, and coming back to that chat shows it live. Sessions with no turn in flight are dropped when the user leaves them (and background ones when their turn ends), so reopening a chat loads it from the DB.
- **The request's `chatId` comes from the session** a message is sent through (`prepareSendMessagesRequest`), not from "the active chat". Sends go through `sendToChat(chatId, …)`; the deferred-create path (first message from Home / a project landing) passes the id of the chat it just created, whose session starts empty.
- **One send at a time from the composer (audit U5).** `page.tsx`'s `sendingRef` is set synchronously when a send starts and released once the message is handed to its chat session — not when the reply ends, so sending from another chat while a reply streams in the background still works. `handleSendMessage` runs in this order: the guards (nothing to send, the open chat's reply still streaming, a send already in progress); `sendingRef` is set; the send waits for the open chat's history load (`awaitChatHistory` — the draft stays in the composer meanwhile; a failed load is retried once, and the send is refused with a toast if it still fails or the user has switched chats); the oversized-request check (a refused send creates nothing and keeps the input); then `takeComposer` snapshots and clears the composer. `sendingRef` is what blocks a second Enter during the history wait and during the deferred-create round-trips (so a double Enter creates one chat); if the create fails, the snapshot is put back (`restoreComposer`) unless the user has started a new message.
- **Turn pipeline** (`useChatPersistence`), in two steps, both for the chat the turn was sent from even if it is in the background. **At turn start** (`onTurnStart` — `useChatSessions` taps each response stream and reports the `start` chunk's metadata the moment it arrives): save the user's image attachments and embed the user's message, against the user row the server just reported. **At turn end** (`onTurnFinish`, from the session's `onFinish`, including stopped and failed turns): generated-image linking → file-part attachments → assistant embedding → persona usage count → summarize gate → auto-memory → title → artifact re-fetch; it also runs the turn-start steps if they have not run. Every chat, project and message id is read from the turn metadata (`readTurnMetadata`); the active chat is consulted only as a UI guard (don't replace the open chat's artifact list with a background chat's).
- A **stopped or failed** turn never receives the `finish` chunk, so its `assistantMessageDbId` is `null` on the client even though the server saved the partial reply. The pipeline then looks the row up with the `getAssistantReplyId(chatId, userMessageDbId)` action (a few short retries) and, when found, writes it into that reply's metadata in the store, so everything that reads a session message's row id from its metadata (Delete, Regenerate, the next request's semantic-exclusion list) sees it too. After a clean finish a `null` id is authoritative: the server wrote no row, or the row is no longer this turn's.
- **On a regenerate** the start metadata reports the existing user row. The turn-start steps skip it when the posted user message carries a DB id (it was saved and embedded on an earlier visit), and the set of handled user rows covers one sent this session.
- **Message Delete and Regenerate** (audit D2) act on DB rows, and **client store ids are never rewritten to DB ids**, so the row id is resolved from the transcript (`resolveMessageDbId` in `chatTurn.ts`): a message loaded from the DB carries its row id as its own id; a reply sent this session carries `assistantMessageDbId` in its metadata; a user message sent this session has no metadata, so its id is the `userMessageDbId` of the reply right after it. `MessagesList` offers the two items only when that id resolves and no turn is in flight in the chat. The unresolved cases stay hidden: a stopped reply until the lookup above writes its id (and for good if the lookup finds nothing), and a user message with no reply after it (stopped before the first token, or failed before the stream) until the chat is reopened from the DB. **Delete** calls the `deleteMessage` action (attachments' Storage objects — except a generated image that an artifact of the same chat still embeds, which is kept (audit R4) — then the row; attachment rows and embedding cascade), then drops the message from that chat's store; a failure shows a toast and keeps the message. Deleting a user message leaves its reply in place. **Regenerate** is offered on the **last** assistant reply only, and only when the message before it is a user message (the server would refuse anything else): `regenerateInChat` calls the session's `regenerate({ messageId, body: { regenerate: true, replaceMessageDbId } })`, so the SDK drops the reply from the store and re-posts the transcript ending at the user message with `trigger: 'regenerate-message'`. Model, effort and grounded mode are the composer's current ones, as for any send. **Restore on failure:** `page.tsx` keeps a copy of the reply the SDK dropped. When the regenerate turn ends with nothing the server would save — the store still ends at the user message it answered (an HTTP refusal or error before the stream, `400`/`409`/`500`; an error part or a Stop before any part), or ends with a reply that has no text or media (only reasoning, or a non-media tool call such as web search, before an error or Stop) — it puts the copy back in that place, replacing the content-less reply; the server wrote nothing, so that copy is still the saved reply. "No text or media" is `replyHasSavedContent` (`chatTurn.ts`), the client mirror of the recorder's persist rule (shares `isMediaToolResult`). A turn that produced content keeps it (the server has replaced the row with it). If the chat's session was dropped meanwhile (the user left), reopening the chat loads the surviving reply from the DB.
- **Chat errors on the banner:** the AI SDK's transport reports an HTTP failure as `Error(<response body>)`, and `/api/chat`'s error bodies are `{ error }` JSON (`apiError`), so `page.tsx` shows the parsed `error` string (`chatErrorText`), never the raw JSON. A stream error's text is shown as is.
- A request that fails before the stream starts carries no metadata: the pipeline does nothing except discard that chat's pending images.
- Because the `start` chunk carries metadata, the SDK puts the reply in the store **before it has any content** (no parts, or only `step-start` markers) and flips `status` to `streaming` at that point. `useChatSessions` keeps such a message out of the `messages` it returns until its first real part (`isPendingReply`), so the staged status line and every "last message" check behave as they did before, and removes it from the store if the turn ends without producing anything (no empty bubble after an early Stop). Side effect: Stop is available from the start chunk rather than from the first token.
