### Context Pipeline (`/api/chat`)

Five layers, in order (all degrade gracefully if providers unavailable):
1. **System prompt** — Always included, never trimmed
2. **Document retrieval** — Top-3 document chunks scoped to the project, from a vector leg (cosine ≥ 0.5, one query embedding shared with semantic retrieval) fused with a keyword leg (see the pipeline below). If the query embedding fails or times out, the keyword leg still serves document context on its own (audit B10).
3. **Semantic retrieval** — Top-5 similar past messages (cosine ≥ 0.7) scoped to the project (a standalone chat: the chat itself). Injected as synthetic context messages after document chunks. Messages the model already sees are left out, in SQL before the LIMIT (audit B9): when `recentTail` sent the whole posted history the route passes `excludeChatId` (no row of this chat, and a standalone chat skips the query outright); when it trimmed, the route passes `excludeMessageIds` = exactly the DB ids of the sent messages (`sentMessageDbIds` in `contextBudget.ts`: loaded ids, `assistantMessageDbId`, a live user message's `userMessageDbId` from the reply after it, and this turn's user row), so messages trimmed off the front stay retrievable. The old dedup compared the client's message ids with DB ids and only matched reloaded messages.
4. **Summary** — Compressed older messages (auto-triggers at 30+ messages, keeps last 10 in full)
5. **Recent messages** — `recentTail` (`src/lib/contextBudget.ts`): every message newer than the chat's `summaryUpToMessageId`, at least 20 and at most 60 (a cut never opens on a reply without its user message). The boundary is placed from the DB ids the client already holds: a loaded message's id, or `assistantMessageDbId` in a live reply's turn metadata; if it cannot be placed, up to 60 are sent (overlap with the summary is harmless, a gap is not). So a failed summarize fold no longer leaves messages in neither layer unless the summary falls more than 60 messages behind (audit B4). With no summary the whole history is sent, capped at 60. Applied to every request, with or without a context prefix (K27).

Embeddings: 768-dim vectors via Gemini `gemini-embedding-001`. `generateEmbedding()` accepts `taskType` (`'query'`/`'document'`) — Gemini uses this for optimization. Retrieval uses **native pgvector** (`findSimilarMessages`/`findSimilarDocumentChunks` run one indexed SQL query each via Drizzle's `cosineDistance`, backed by HNSW indexes).

**Advanced retrieval pipeline (Phase B2, hybrid-fused in RAG Phase 3)** — `src/lib/retrieval.ts` `retrieveContext()` orchestrates: **query-rewrite** (`queryRewrite.ts`, Gemini Flash → standalone query) → embed → **vector top-N** (default 20) **∥ keyword top-N** (`keywordSearch.ts` `findChunksByKeyword`, documents path only) → **RRF fusion** (`rrf.ts` `rrfFuse`, documents path only — merges both ranked lists by `score = Σ 1/(RRF_K + rank + 1)`) → **MMR** diversity (`mmr.ts`, λ 0.7) → **LLM rerank** (`rerank.ts`, Gemini Flash) → top-k (docs 3 / msgs 5). The keyword leg's FTS half OR-joins the question's words (`ftsOrQuery`: letters/digits only, `or` dropped, at most 32 terms) before `websearch_to_tsquery`, so a natural question matches chunks holding some of its words and `ts_rank_cd` ranks those holding more first; it used to AND every word and matched nothing once one was missing (prior audit D1). Its other half is trigram `ILIKE` on identifier tokens (`SW-101`). **MMR keeps the fusion (audit B5):** every chunk the keyword leg found — keyword-only hits (no embedding) and chunks both legs found — is exempt from MMR (top `docTopK` by RRF score); the remaining embedded chunks go through MMR with the **normalised RRF score** as relevance (`MmrItem.relevance`, falling back to cosine similarity when the keyword leg returned nothing). The MMR picks and the exempt chunks are then merged by RRF score, each list keeping its own order, and that list goes to rerank — rerank's fallback (and the no-rerank path) is a head slice of it, so a chunk found by both legs can never fare worse than one found by keyword alone. Before this, MMR re-ranked by raw similarity and dropped the top fused chunk when it sat low in the vector list. Every stage is **best-effort and degrades to the prior stage** (with all toggles off it's plain vector top-k; a keyword-search failure logs and degrades to vector-only; a query-embedding failure skips the vector queries and the message leg but keeps the keyword leg, which starts at once alongside the embedding). **Fail-fast Gemini stages (audit B11):** query rewrite, the query embedding and both reranks run with `maxRetries: 0` and an `AbortSignal.timeout(RAG_STAGE_TIMEOUT_MS)` (default `4000`), raced by `withStageTimeout` (`src/lib/stageTimeout.ts`) so the bound holds even if a call ignores the signal; on timeout rewrite falls back to the raw question, the embedding to the keyword leg, rerank to the incoming order. Worst case before the first token is about three stage timeouts (rewrite → embedding → rerank). Ingestion's document embeddings keep the SDK's retries (`generateEmbedding` without options). All knobs live in `src/lib/ragConfig.ts` (`getRagConfig()`) with env overrides: `RAG_DOC_THRESHOLD`, `RAG_MSG_THRESHOLD`, `RAG_TOP_N`, `RAG_DOC_TOP_K`, `RAG_MSG_TOP_K`, `RAG_MMR_LAMBDA`, `RAG_REWRITE_ENABLED`, `RAG_RERANK_ENABLED`, `RAG_MMR_ENABLED`, `RAG_HYBRID_ENABLED` (default `true`), `RAG_RRF_K` (default `60`), `RAG_KEYWORD_TOP_N` (default = `RAG_TOP_N`), `RAG_STAGE_TIMEOUT_MS` (default `4000`; zero or negative falls back to the default). Hybrid scope is **document chunks only** — message-side retrieval stays vector-only (no observed failure case). Note: rewrite + rerank add two Gemini Flash calls per message (~1–2s latency) — toggle off via env if needed. Reranking/rewrite LLM calls reuse the proven `generateText`+parse+fallback pattern (like `classify`).

**Whole-document mode (RAG Phase 3)** — top-k chunk retrieval structurally can't answer set-wide questions ("list every storm sheet") no matter how large k is. The `read_document` tool (`src/lib/documents/tool.ts`, `createReadDocumentTool`) lets Claude read a project document's full extracted text window-by-window instead: source is `extracted.txt` in Storage (`documents/<projectId>/<docId>/[revN/]extracted.txt`, persisted since RAG Phase 1); windowing (`src/lib/documents/windowing.ts` `sliceWindow`) cuts on `# Page n` anchors when present (vision/hybrid docs emit them) or falls back to character-offset windows, capped at `READ_DOC_WINDOW_CHARS` (default `100000` chars ≈ 25k tokens) per call, with a continuation pointer (`nextOffset`/`fromPage`) when more remains. Wired into `/api/chat` for Claude project chats with ≥1 `ready` document alongside a compact `[Project documents]` manifest (id/filename/pageCount/charCount/extractionMethod/extractionPartial — one DB query) and `READ_DOCUMENT_GUIDANCE`: chunks-first for targeted questions, `read_document` for set-wide/exhaustive asks or when chunks are visibly insufficient. Missing `extracted.txt` (pre-Phase-1 docs) or Storage errors degrade to an in-band tool error, never a throw. Sweep budget is the existing `stopWhen: stepCountIs(12)`. **Tool outputs are not persisted** — `/api/chat` saves the assistant turn server-side (`createAssistantTurnRecorder` in `src/lib/chatTurn.ts`) and records the stream's TEXT deltas only, so `read_document` window text never reaches the `messages` table (reload shows the answer without a tool card, same as `web_search`). Within a live session the tool parts do stay in the client's message store and are re-sent with each request, so the route stubs them: `stubOldToolOutputs` (`src/lib/contextBudget.ts`) replaces the `output` of every `read_document` part outside the last assistant turn with `{ stubbed: true, documentId, fromPage?, nextOffset?, note: 're-read if needed' }` before conversion, keeping the call so each tool call still pairs with a result (audit B3). A tool call left without a result (Stop or a dropped connection mid-tool) is dropped by `convertToModelMessages(…, { ignoreIncompleteToolCalls: true })`; without it the SDK threw `MissingToolResultsError` and every later send failed until a reload (audit B1). An active `read_document` tool part drives the **`reading-documents`** chat stage (`src/lib/chatStage.ts`) → `ThinkingStatus` "Reading documents…".

**Grounded & Cited Answers (shipped in v4.53.0; migration `0017` applied)** — answers cite their sources and can be restricted to project documents. Server side: retrieved chunks carry self-describing headers `[Source: doc 12 "plans.pdf" p.34–36 §c456]` (`retrieval.ts`; the filename here and in the `[Project documents]` manifest passes through `promptSafeLabel()` (`src/lib/promptSafe.ts` — strips quotes, brackets, angle brackets, backticks and control/format characters, caps at 120 chars) because filenames are untrusted (a web page's H1 becomes one); pages from the new `page_start`/`page_end` chunk columns, `§c` chunk anchor always present); `CITATION_GUIDANCE` (chat route) instructs Claude to end document-derived sentences with `[cite:12 p34]`-style markers copied from those headers — grammar's single source of truth is `CITE_RE` in `src/lib/citations.ts` (`[cite:<doc>]`, `p<n>`, `p<a>-<b>`, `c<chunk>` forms); `GROUNDED_GUIDANCE` (request `grounded: true`) additionally forbids general-knowledge fallback (verbatim gap phrase: `Not found in project documents`); request `excludedDocumentIds` filters retrieval (both legs), the manifest, and `read_document` (in-band error). Citation compliance is logged via `streamText`'s server `onFinish` (`[cite-compliance]`). Client side: a remark plugin (`src/lib/remarkCitations.ts`) turns markers into `CitationChip`s (unknown-doc markers stripped; pages clamped; trailing half-streamed markers hidden via `hideIncompleteTrailingCite`); chips open `DocumentPreviewDialog` with `target: { page?, chunkId? }` (PDF `#page=N` fragment, or Extracted-text scroll+highlight by `data-chunk-id`). Grounded control: persona flag (`grounded: true` on Contract Abstract / Contract & Spec Analyst / Plan & Spec Reader) + composer pill (`useGroundedCompose` — user pick wins, reset on chat open, pill always visible when ON). Scoping: **per-project** checkboxes in the Files rail (`useDocScope`, localStorage `project-doc-scope-<id>`; per-chat scoping is a spec follow-up). ⚠️ **Tailwind scanner gotcha**: literal `[cite:` + digits in a scanned source file becomes an arbitrary-property CSS candidate and can BREAK cold builds — `globals.css` has `@source not` exclusions (tests/, docs/, e2e/, `src/app/api`, `citations.ts`, `documents/tool.ts`); never write literal markers in other scanned files (describe, don't exemplify) and keep gate builds cold (`rm -rf .next`).

**Vision extraction (Phase C2, reworked in RAG Phase 2 v4.45.0)** — `src/lib/visionExtraction.ts` handles two paths: `extractViaVision(buffer)` splits the PDF into page-range segments via `src/lib/pdfSegments.ts` (**pdf-lib**; default 20 pages/segment, each kept under Gemini's 50MB-per-request PDF cap with recursive halving) and sends each segment **inline as a native PDF** (`file` part) in one Gemini call — bounded concurrency (`src/lib/concurrency.ts`) + retry; Gemini reads the embedded text layer natively and sees each page as an image (no per-page rasterizing; `pdfjs-dist`/`@napi-rs/canvas` remain only for thumbnails). `extractViaVisionImage(buffer, mimeType)` vision-extracts a single image. Both degrade to `''` if no Gemini key. The vision fallback triggers on thin text **absolute** (`EXTRACTION_MIN_TEXT_CHARS`, default `100`) **or per page** (`EXTRACTION_MIN_CHARS_PER_PAGE`, default `200` — catches CAD plan sets whose only text layer is title blocks). Env knobs: `EXTRACTION_MODEL` (default `gemini-3.5-flash`), `EXTRACTION_MAX_PAGES` (default `500`), `EXTRACTION_SEGMENT_PAGES` (default `20`), `EXTRACTION_SEGMENT_CONCURRENCY` (default `2`), `EXTRACTION_SEGMENT_MAX_BYTES` (default 45MB), `EXTRACTION_MAX_OUTPUT_TOKENS` (default `60000`; `finishReason==='length'` flags the doc partial), `EXTRACTION_SEGMENT_RETRIES` (default `2`). A failed segment, skipped oversize page, output truncation, or page-capping all surface as `extraction_partial` — never silent. Once text is extracted the downstream chunk → embed → pgvector RAG pipeline is unchanged. **Per-page hybrid splice (v4.46.0)** — a document-level density gate can't see a text-rich plan set with individually sparse sheets (AutoCAD SHX notes sheets: stroke-geometry text, title-block-only text layer). On the text path, pages whose own text layer falls under `EXTRACTION_HYBRID_PAGE_MIN_CHARS` (default `500`) are grouped into contiguous runs and vision-extracted via `extractPagesViaVision`/`splitPdfPageRuns` (reusing the v4.45.0 segment machinery), then spliced back into the document text in page order; more sparse pages than `EXTRACTION_HYBRID_MAX_PAGES` (default `80`) skips hybrid entirely (the whole-doc gate owns pervasively-sparse docs). `extraction_method` becomes `'hybrid'` (a `hybrid` chip in `DocumentCard`, alongside `vision`); the splice is best-effort and never fatal — a hybrid failure just keeps the plain text. **Failed-page tracking + provenance tags (RAG Phase 3, v4.48.0)** — a segment that fails after retries, or an oversize page that's skipped, records its absolute page range into `ExtractionResult.failedPages`, plumbed via `/api/documents/process` → `documents.failed_pages` (jsonb) → `GET /api/documents` → `DocumentCard`'s Partial tooltip ("Vision failed on pages 12–14, 30") and `read_document`'s `unavailablePages`. Separately, every vision-derived page run gets a `[pages 12–14 · vision]` header (`visionRunHeader` in `src/lib/visionExtraction.ts`) prepended to its text before chunking — in `extractViaVision`'s joined output and in the hybrid splice — so Claude can hedge on OCR-derived content; no schema change, no backfill.
